**Дата:** 2026-10-11 · **Ревьюер:** ассистент Пола · **База проверена живыми запросами** (service-role, read-only)

Файлы: `funcs.txt` (Yandex Cloud Functions, YDB-ветка + ветка Supabase) и `supafuncs.txt`
(тонкий PostgREST-клиент + `SupabaseBookingService`).

## TL;DR

Скелет правильный: колонки, которые использует код (`rentals.vehicle_id`, `requested_start_date/end_date`,
`status`, `payment_status`, `users.user_id`), **реально существуют и называются именно так**. Записи
успешно создаются: в базе уже лежат 2 тестовые аренды от агента (`avito_Q1-…`, `avito_u2i-…` от 10.10).
Но: **(1)** листинг без фильтра `type='bike'` предлагает куртки и услуги как «мото», **(2)** даже с
заданным `SUPABASE_CREW_ID` перебор 147 машин × 2 запроса — почти гарантированный таймаут функции,
**(3)** нет валидации окна → в базе уже мусор (одна аренда с `end < start`), **(4)** часовой пояс:
веб-приложение пишет московское время (+03:00), а код бездумно лепит «Z» → сдвиг 3 часа, **(5)** нет
повторной проверки доступности перед вставкой (гонка) и нет льготы 30 мин / пропуска «протухших» строк,
как в канонической логике приложения. Готов фикс: `docs/avito-agent/supafuncs-fixed.cs` (drop-in) +
опциональный RPC `docs/sql/owner/20261011_avito_agent_try_create_rental.sql` (SQL исполняет owner).

## 1. Что уже работает (проверено живыми запросами)

| Проверка | Результат |
|---|---|
| `cars?id=eq.falcon-lynx-purple&select=id,make,model,daily_price,quantity,owner_id,crew_id,type` | 200, `quantity=1`, все поля есть |
| Пересечение по Kawasaki (сейчас активная аренда 09.10 15:00Z → 11.10 15:00Z) | 200, вернулась именно та строка `status=active` |
| Синтаксис `status=not.in.(cancelled,completed)` | 200, валиден |
| Upsert `users` c `user_id='avito_…'` | работает — 5 юзеров `avito_*` в базе |
| INSERT аренды (`pending_confirmation` + `interest_paid`) | работает — 2 строки от 10.10 |

Ключевой факт: **`users.user_id` — колонка типа text**, поэтому `avito_{chatId}` валиден (страшного
ограничения «user_id только числовой TG-id» нет; существующие числовые значения — это просто TG-id,
хранящиеся в text).

Реальные статусы в `rentals` (сегодня): `cancelled` 18, `completed` 234, `pending_confirmation` 6,
`active` 3. Жизненный цикл в приложении: `pending_confirmation → confirmed → active → completed`.

## 2. Каноническая логика доступности в веб-приложении (с чем сверяться)

Источник: `app/franchize/actions-runtime.ts → checkFranchizeCarsAvailability` +
`app/franchize/lib/rental-overlap.ts`. Правила, которые приложение применяет при заказе с сайта:

1. **Блокирующие статусы:** `["pending", "pending_confirmation", "confirmed", "active"]`.
2. **Окно строки аренды:** `requested_*` приоритетны, `agreed_*` — фолбэк; если нет конца —
   «старт + 24ч»; если нет старта — «конец − 24ч».
3. **Льгота на возврат:** +30 минут к концу аренды (`RENTAL_BLOCK_GRACE_MS`).
4. **Протухшие строки не блокируют:** если конец (+30 мин) уже в прошлом — строка игнорируется
   (забытая `pending_confirmation`-дубль не держит байк «занятым»).
5. **Часы точные** (не календарные дни): чекаут сайта пишет requested_* в московском времени (+03:00).

Код агента сейчас сверяется с этой логикой частично — см. расхождения ниже.

## 3. Проблемы (по убыванию серьёзности)

### 3.1. CRITICAL — листинг предлагает куртки/услуги вместо мото
`ListFreeCarsAsync` не фильтрует `cars.type`. Для vip-bike выборка — **147 строк**:
62 equipment, 47 service, 6 wb_item и только **32 байка**. Агент честно «предложит арендовать
куртку Toxic Green». А до установки `SUPABASE_CREW_ID` фильтра не было вообще — выборка
**277 строк со ВСЕХ экипажей** платформы (это и есть те «277 строк… там не ток байки, но экип и
подушки даж» — точное попадание).
**Фикс:** `&type=eq.bike`, плюс отрезать служебное: `is_test_result=eq.false`, скрытое из каталога
(`specs->>hidden` не true — таких 5 у vip-bike).

### 3.2. CRITICAL — почти гарантированный таймаут даже после установки crew_id
`ListFreeCarsAsync` → на каждую из 147 машин вызывается `CheckAvailabilityAsync`, который **повторно**
тянет ту же машину и аренды. Итого ~294 последовательных HTTP-запроса к Supabase из Yandex Cloud
Function (по ~150–300 мс каждый = 45–90 с). Вот почему «returned error»: скорее всего это был таймаут
функции, а не ошибка Supabase. Установка `SUPABASE_CREW_ID` сокращает выборку, но не лечит саму
схему «N+1 × 2».
**Фикс:** два запроса всего — один `cars?…&crew_id=eq.…&type=eq.bike` и один
`rentals?vehicle_id=in.(…)&status=in.(…)` с разбором в памяти (как делает веб-приложение).

### 3.3. HIGH — нет валидации окна бронирования (мусор уже в базе)
Доказательства в базе: аренда `3bc69a27…` — `requested_end_date` (14:09:15) **раньше**
`requested_start_date` (14:09:17); аренда `0ffb583c…` — даты из сентября на месяц в прошлом
относительно момента создания. Модель агента передала мусор — функция приняла.
**Фикс:** `end > start`, `start ≥ now − 2ч`, длительность ≤ 30 суток; иначе понятная ошибка 400
(«проверь даты: конец раньше начала» и т.п.).

### 3.4. HIGH — часовой пояс: сдвиг на 3 часа
Веб-чекаут пишет `requested_*` как московское время (+03:00); фильтры приложения считают окна в MSK.
Код агента делает `startDate.ToString("yyyy-MM-ddTHH:mm:ssZ")` — молча трактует наивное время как UTC.
Если модель передаст «13:00» (имея в виду МСК), в базе окажется 16:00 МСК.
**Фикс:** наивное время (Kind=Unspecified/Local) трактовать как **Европа/Москва (+03:00)** и
конвертировать в UTC; форматировать через `CultureInfo.InvariantCulture` (разделитель «:» в кастомном
формате — культуразвисимый, на ru-RU-сервере можно словить сюрприз). Конфиг `AVITO_TZ_OFFSET_HOURS=3`.

### 3.5. HIGH — гонка при бронировании
Check → Book без атомарности: два параллельных вызова оба пройдут проверку и создадут брони на одно
окно. В коде это честно закомментировано («при росте нагрузки — вынести в RPC»).
**Фикс:** приложен SQL-файл `try_create_avito_rental()` (advisory lock по vehicle_id + проверка
пересечения + вставка в одной транзакции; SQL исполняется владельцем вручную — как договорились).
До внедрения RPC достаточно повторной проверки внутри `CreateBookingAsync` (сужает окно гонки с
секунд до миллисекунд).

### 3.6. MEDIUM — расхождения с правилами приложения
- Агент не умеет фолбэк `requested_* → agreed_*` (сегодня все строки имеют requested, но контракт
  данных приложения — оба поля).
- Нет правила «протухшие не блокируют» (конец + 30 мин в прошлом) и льготы 30 мин вообще.
- Блокирующие статусы: агент `not.in.(cancelled,completed)` (fail-open для новых статусов),
  приложение `in.(pending,pending_confirmation,confirmed,active)`. Сегодня множества совпадают;
  для консистентности фикс использует список приложения.

### 3.7. MEDIUM — скрытые/тестовые машины видны агенту
5 байков vip-bike помечены `specs.hidden=true` (Suzuki GSX-S1000F, Kayo TSD 110, Wenbox U2 Pro,
BMW S1000RR Electro Silver, Ducati Panigale S Electro Black Chain) — агент их предложит. Плюс
колонка `is_test_result` (сейчас у vip-bike пусто, но заполнение — вопрос времени).

### 3.8. LOW
- **N+1** — см. 3.2 (частично тот же фикс).
- **`interest_amount` не заполняется** при `payment_status='interest_paid'` — в приложении
  markdown-doc пишет `interest_amount: 0`. Лучше писать 0 (или сумму задатка) — иначе у оператора
  «оплачен интерес» с пустой суммой.
- **`total_cost` не считается** — можно писать предварительную оценку `daily_price × дней` (у
  falcon-lite-2026 цена 0 → писать null и отдавать агенту «цена по запросу»).
- **`metadata.source` не ставится** — оператор не видит в карточке аренды, что она из Авито.
  Фикс: `metadata: {source:'avito-agent', avito_chat_id}`.
- **Ответ `CheckAvailability` в Supabase-ветке беднее YDB-ветки** (нет `nearest_booking_before/after`)
  — модели агенту полезно получать окно конфликта («занят до 15:00») — добавлено в фикс.
- `quantity` — агент учитывает (у `y-volt-surge-v` quantity=2 — правильно), а веб-приложение, к
  слову, блокирует при любой пересечке независимо от quantity (консервативнее). Расхождение не
  вредное, но знай: сайт заблокирует второй байк, агент — разрешит.
