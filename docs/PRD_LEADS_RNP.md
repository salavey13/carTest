# PRD: Единый конвейер лидов «РНП» — Avito, каналы, CRM и KPI

> **Статус:** draft v1 · **Дата:** 2026-08-31 · **Владелец:** Pasha / команда VIP BIKE
> **Связанное:** `docs/AVITO_WEBHOOK.md` (v1 интеграция), `docs/PRD_LIFECYCLE_MESSAGING.md`
> **Термин:** РНП — «Рука На Пульсе», управленческий контур оцифровки воронки (см. протокол встречи CRM/РНП).

## 1. Контекст и проблема

Стратегическая сессия зафиксировала узкое место бизнеса: **менеджеры задерживают
ответы на входящие заявки и «солят» лиды**. Реклама приводит трафик, но без
оцифровки ранних стадий (первичный контакт → качественный контакт → КЭВ → дожим)
потери не видны и не управляемы.

Дополнительная проблема — **разобщенность систем**: сообщения Авито обрабатывает
отдельный ассистент-бот (с предложениями ответов), сайт/бот команды пишут в
Supabase, а ранние (холодные) обращения не попадают в CRM — менеджер видит лида
только на «горячих» стадиях (тест-драйв/аренда/продажа), когда часть воронки
уже потеряна.

**Цель продукта:** все входящие обращения из всех каналов (Авито, сайт, TG, ВК,
Директ, Карты) попадают в единую CRM-ленту лидов в момент первого контакта,
с каналом, SLA первого ответа и сквозной воронкой до сделки — это фундамент
для KPI-мотивации и CPL-аналитики.

## 2. Аудит текущего состояния (по коду, факт)

### 2.1 Что является канонической CRM (живое)

| Компонент | Что делает |
|---|---|
| `public.franchize_intents` | **Канонический лиджер.** Пишется `upsertFranchizeLead()` (`app/franchize/lib/leads.ts`) из всех web-flow: callback, /doc, /testdrive, корзина, dashboard. CHECK-констрейнты: intent_type (16 значений), stage (20 значений), `contact_channel` — свободный text |
| `/franchize/[slug]/leads` | Leads-страница CRM. `server-actions/leads.ts` агрегирует **5 источников**: `franchize_intents` + `rental_contract_artifacts` + `user_rental_secrets` + `rentals` + sale/testdrive артефакты. Стадии дербятся в `pipeline-stages.ts` (new → contacted → … → closed), сегменты hot/warm/verified/troubled |
| `lead_notes` | Заметки по лиду со страницы — живой |
| `server-actions/leads-kpis.ts` | KPI-агрегаты для страницы (mode rent/sale/service) — база для РНП-дашборда |
|-dismiss `leads-dismiss.ts` | Причины отклонения (not_interested, unreachable, …) — живой |

### 2.2 Avito v1 — сделано (2026-08-31)

- `POST /api/webhooks/avito` — приём Messenger v3 webhook:
  первое сообщение покупателя → **холодный лид** в `franchize_intents`
  (`intent_type=callback_request`, `stage=lead_captured`, `contact_channel=avito`,
  metadata: avitoChatId, itemTitle, текст); повторные — update `last_seen_at`;
  наши ответы — только touch. Дедуп по chat_id, идемпотентность по event id,
  всегда 200 (таймаут Авито 2 сек).
- TG-уведомление владельцу экипажа о новом лиде (через `/api/forward-telegram`,
  т.к. на VPS Telegram заблокирован).
- Скрипт подписки `scripts/avito-webhook-setup.mjs` (register/unsubscribe).
- Секрет `AVITO_WEBHOOK_SECRET` задан в VPS `.env.local`.
- **НЕ активировано:** подписка на стороне Авито (нужны `AVITO_CLIENT_ID/SECRET`
  со scope `messenger:read` из приложения на developers.avito.ru).

### 2.3 Legacy / мёртвое (подозрение владельца подтвердилось)

| Объект | Статус | Вердикт |
|---|---|---|
| Таблица `leads` + `app/leads/` (`/leads`) | Живой код, но это **старый отдельный тул** (скрапер kworks/hotvibes, линкуется из `/nexus`). К франшизной CRM отношения не имеет | Не трогать в рамках РНП; в фазе 3 — переименовать/заморозить, чтобы не путал |
| `public.crm_leads` + `resolve_crm_lead()` (foundation 2026-07-21) | **Мёртвый фундамент:** 0 ссылок в `app/` — таблица создана, кодом не читается и не пишется | Фаза 3: либо становится identity-spine (merge по телефону), либо drop |
| Ассистент-бот Авито | Внешняя система: отвечает/предлагает ответы, **в CRM не пишет** | Фаза 2: dual-write через общий ingest |

**Ключевой вывод:** «таблица leads» — легаси старого скрапер-тула. Реальная CRM —
`franchize_intents` + leads-страница франшизы. Путаница из-за одинаковых имён.

## 3. Целевая архитектура (v2)

```
Каналы                     Единый ingest (franchize_intents)          Потребители
──────                     ────────────────────────────────           ───────────
Авито чаты ──────┐         contact_channel: avito                    Leads-страница
  └─ ассистент-бот├──►     intent_type: callback_request/rent/sale   (холодные в «Новых»)
Авито webhook v1 ┘         stage: lead_captured → …                  TG-уведомления
Сайт callback ───┐         metadata: атрибуция, SLA, КЭВ-факты       РНП-дашборд (E5)
TG-бот команды ──┼──►                                                 Дайджесты (E7)
ВК / Директ / ───┤                                                    KPI-выгрузка (E8)
Карты (офлайн) ──┘                                                    Мотивация РОПа
```

Принципы:
1. **Один лиджер** — `franchize_intents`. Новые каналы = новые значения
   `contact_channel`, не новые таблицы.
2. **Ingest отделён от ответов:** ассистент-бот Авито продолжает предлагать
   ответы, но обязан дублировать факт обращения в общий ingest (webhook API
   или RPC `capture_avito_message`), иначе CRM слепа к обработанным чатам.
3. **Метрики — из metadata JSONB** (эволюционно, без ломки CHECK): сначала
   собираем факты, потом строим KPI.
4. **РНП-слой читает, не пишет:** дашборд/дайджесты — проекции над intents.

## 4. Модель воронки РНП → стадии системы

| Этап воронки (бизнес) | Метрика / KPI | Стадия/данные в системе | Как фиксируем |
|---|---|---|---|
| **Первичный контакт** | Кол-во обращений (лидов) | `lead_captured` | Авито webhook, callback, боты — автоматом |
| **Качественный контакт** | Эффективные касания (≥40 сек), **скорость первого ответа** | `contacted` + metadata `firstResponseAt`, `responseMinutes` | E2: первый ответ оператора (кнопка/действие/answer бота) |
| **КЭВ** (ключевой этап) | Назначенные/проведённые тест-драйвы, визиты в шоурум | `test_ride_requested` / `test_drive` / metadata `visitAt` | Уже пишется из /testdrive-flow; визит — E4 |
| **Дожим и финал** | КП/счета, повторные касания, закрытые сделки | `offer_sent`, `manual_reserved`, `contract_generated`, `payment_confirmed`, `closed_won/lost` | Частично есть (closer-стадии); КП-факт — E6 |
| **Отклонение** | Причины потерь | `dismissed` + причина (10 причин уже в UI) | Живой `leads-dismiss` |

Блоки РНП (ответственные): **Маркетинг** — CPL по каналам (нужны бюджеты:
metadata-справочник или ручная таблица `channel_spend`); **Первичные продажи** —
скорость ответа, взятые в работу, КЭВ, сделки; **Повторные продажи** — LTV,
повторные аренды (rentals по crm-identity), допродажи.

## 5. Бэклог улучшений

### Фаза 0 — готово ✅
- **E0. Avito → холодные лиды:** webhook v1 (см. §2.2). Остаток: активировать
  подписку ключами Авито, задать `AVITO_WEBHOOK_SECRET` в Vercel env.

### Фаза 1 — быстрые победы (1–2 недели)
- **E1. Пометка канала в UI:** бейдж `contact_channel` в карточке лида
  («Авито» / «Звонок» / «TG»), фильтр по каналу. *(бейдж «Заявка» уже добавлен)*
- **E2. SLA первого ответа:** фиксация `firstResponseAt` — триггеры:
  оператор перевёл стадию в `contacted`, отправил TG/Авито ответ (бот),
  или кнопка «Взял в работу». Метрика: медиана/90-перцентиль responseMinutes
  в разрезе менеджера. **Accept:** на странице видно «ответил за N мин», сортировка «дольше всех ждут».
- **E3. Раздел «Холодные» в сегментах:** сегмент `new` (lead_captured, не
  взятые в работу > 15 мин → подсветка). **Accept:** менеджер видит просрочку без выгрузок.
- **E4. Факт визита/КЭВ:** кнопка «КЭВ состоялся» (visit/testdrive) в карточке
  лида → metadata `kevAt`. **Accept:** счётчик КЭВ за день/неделю на дашборде.

### Фаза 2 — контур РНП (2–4 недели)
- **E5. РНП-дашборд** (`/franchize/[slug]/rnp`, переиспользует `leads-kpis.ts`):
  блоки Маркетинг / Первичные / Повторные; воронка по этапам §4; фильтр периода.
  **Accept:** планерка проводится по цифрам дашборда, не по Excel.
- **E6. Атрибуция и CPL:** UTM/`?from=` на callback и корзину; справочник
  бюджетов каналов (месяц, сумма) → CPL = бюджет / лиды канала.
  **Accept:** CPL по Авито/сайту/Директу за месяц.
- **E7. TG-дайджесты:** утренний (вчерашние лиды/SLA-просрочки) + вечерний
  (КЭВ, сделки, неотработанные) в чат руководства; расширить существующий
  `daily-insights` cron. **Accept:** дайджест приходит без ручного запроса.
- **E8. Двойная запись ассистент-бота Авито:** бот при каждом обращении дергает
  `POST /api/webhooks/avito/ingest` (или RPC) с фактом чата/ответа → лиды не
  зависят от того, кто ответил первым — бот или webhook.
  **Accept:** 100% чатов Авито, обработанных ботом, видны в CRM.

### Фаза 3 — гигиена и фундамент (по мере надобности)
- **E9. Legacy-разбор:** `/leads` (скрапер) — переименовать маршрут в
  `/tools/scraper` и вынести из меню `/nexus`; таблицу `leads` заморозить
  (read-only), мигрировать нужное (если есть) в intents.
- **E10. Identity-spine:** решение по `crm_leads`: либо внедрить (merge
  лидов по телефону при QR-claim через `resolve_crm_lead`), либо drop.
  Критерий: один клиент = одна карточка во всех разделах.

| Обращения Авито в CRM | 100%, задержка < 1 мин |

| Лиды, взятые в работу < 15 мин | ≥ 80% |

→ Регламенты/планерки → Делегирование РОПу** — продукт идёт впереди нормативов:
сначала факты, потом нормы, потом мотивация.
